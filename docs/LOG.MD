## 日志系统

目前首要任务是把日志从签到独立出来，它现在已经开始变得难用了

## 设计目的

现在通过operation识别操作以及变得极其复杂难用，每新增一种操作就要修改大量文件，极有可能疏忽，所以打算对日志进行一次重构

在设计新系统时候也注意到可以把一些更底层的事情做了，比如指令统计，消息识别等

## 设计构想

### 架构

目前设想由3层构成

第一层是消息层，会记录所有收到的消息包括内容，图片什么的文件不会下载到本地，只记录

第二层是指令层，如果该消息倍判定为指令，就会在这一层记录谁执行了什么指令，目前已经有该设计结构的有maimai插件，我给他做了自然语言指令适配

第三层是事件层，如果该指令对数据库做出了改动，比如现在的签到抢劫等，那么就会在这一层记录什么指令引发了什么事件，同时也会记录事件详细信息，比如获得1MB就会记录，这层可以不一定依赖指令

整体指向是：message_id（消息id） -> command_id（指令id）和 event_id（事件id）

### ID

识别事件不会再用type识别了，我打算弄成只通过大类识别，比如不管你签到还是抢劫，都属于data变动，签到获得物品，或者未来加了使用物品，那就都算item变动，会根据这些大类构建单独的表，比如data_logs、item_logs

type记录方式也会对应改变，同一类的也会记录在一起，我会采用命名空间的形式记录，比如签到是checkin.checkin，补签是checkin.makeup，如果还有子类那就继续分下去，这个可以叫event_key

同时这种明明方式也会决定文件的存储结构，放到下面一块再说

logs.db将会把所有日志有关内容全都包括进去，并提供统一接口，各个插件不再独立使用自己日志库或者尝试访问其他插件的，插件表名会带上“插件名_”的前缀，通用表名比如上面说的那几层，就正常命名

### 存储

我打算把log当一个插件，虽然它本身不需要提供一些指令，但是还是做了

它的核心在于storage/log和services/log两个文件夹，我会按照事件分类在内部构建单独的子文件夹，这样以后使用接口会好用很多，比如补签（checkin.makeup）有关的操作我会放到/log/checkin/makeup.py里，然后使用时候就只需要log.checkin.makeup.操作()

它本身也需要提供一些统一的接口，比如识别事件类，初始化表等，这一块是核心需要好好设计

## 功能

打算做的功能有这些

- 消息统计，记录所有消息，为其他消息统计类插件提供服务，比如字符统计，词云，未来想做的年终总结等等
- 指令统计，用于记录各个插件指令调用频率，虽然bot用的人少，但是这是顺手的事
- 各个插件的各自日志记录

## 边界

仅用于存储日志类数据，不存储插件的各自独有数据，比如签到的用户数据，这个不可以往这里放，这个需要每个插件独自管理
